# キャラクター作成ボーナスの解析

2026-10-21。対象は手元のFCⅠ・Ⅱ・Ⅲと、それぞれのパラメータ変更版の計6本。初回解析時はアプリ・ROM・既存セーブを変更していない。後に下記の設定をアプリ接続層へ追加した。

## 結論

64（十進）は原作の最大ボーナスではない。初期ボーナスを64にするだけでは、割り振りの上限に達しても残りポイントが消えず、原作の作成確定条件を満たせない。

|作品|原作が生成する最大ボーナス|割り振り可能な総量|
|---|---|---|
|Ⅰ|全種族29|人間62、エルフ60、ドワーフ60、ノーム59、ホビット58|
|Ⅱ|人間62、エルフ60、ドワーフ60、ノーム59、ホビット58|生成最大値と同じ|
|Ⅲ|全種族60|全種族60|

Ⅰ・Ⅱは各能力値18まで。Ⅲは各能力値が種族初期値＋10までで、ホビットの素早さ初期値もⅠ・Ⅱとは異なる。64を与えた場合、Ⅰ・Ⅱは種族順に2/4/4/5/6点、Ⅲは4点が残る。

実装時は次のどちらを狙うかを区別する。

- 「原作で自然に出る最高ボーナス」: Ⅰは29、Ⅱは種族別最大、Ⅲは60。
- 「全能力値を上限まで上げられる最大配分」: Ⅰ・Ⅱは種族別の残り容量、Ⅲは60。Ⅰでは自然生成の範囲を超える。

希望が全能力値への最大配分なら、固定64ではなく、種族初期値と能力上限から配分総量を計算して設定する方式が適切。64という数値そのものを必須にする場合は、余りの破棄、確定条件の変更、能力上限の引き上げのいずれかも必要になる。

## 原作コードの位置

以下はCPUアドレス。ⅠはPRG16KiB bank 6と固定bank 7、Ⅱ・Ⅲは固定PRG8KiB bank 14（CPU $C000～$DFFF）を対象とする。ファイルオフセットやWikiのエミュレーター用表記とは分ける。

|項目|Ⅰ|Ⅱ|Ⅲ|
|---|---|---|---|
|生成処理|$9D5D～$9D7B|$DBDF～$DC03|$DBAF～$DBD3|
|残りポイント RAM|$025B|$0040|$0040|
|割り振り能力 RAM|$0254～$0259|$004D～$0052|$004D～$0052|
|種族の初期能力|固定bank $EF52＋種族×8|固定bank $DC20＋種族×6|固定bank $DC0B＋種族×6|
|Ⅱの種族別ボーナス上限表|―|$DC1B～$DC1F = 3E/3C/3C/3B/3A|―|
|種族番号|$0251|$0041|$0041|
|選択中の能力番号|$002C|$0036|$0036|
|1点加算|$9E2E～$9E47|$D579～$D589|$D559～$D56C|
|1点返却|$9E4A～$9E5D|$D58A～$D596|$D56D～$D579|
|確定時の残りポイント検査|$9DDE～$9DE1|$D464～$D466|$D456～$D458|

Ⅰの生成は0～4の乱数＋5を初期値にし、続く2回の乱数判定それぞれで条件成立なら10を加算する。上限は9＋10＋10＝29。

Ⅱは初期5～9に、乱数判定が続く限り10を加算する。CMP #09の成立時のCarryもADCに入るため、加算部分だけを読むと9に見えても実際には10増える。59以上となった経路で種族別上限表へ置き換える。

Ⅲは初期5～9に、乱数判定が続く限り10を加算するが、60以上になった時点で60へ丸める。

確定時は残りポイントが0であることを要求する。職業候補も別に必要だが、64固定ではその前提の0点条件が満たせない。

## 実装に必要な接続

既存binjnes（MIT）のRAM書込コールバックを再利用できる。新しいエミュレーターや乱数・割り振り処理の自作は不要。

残りポイントを毎フレーム固定してはいけない。原作が1点ずつ減らせなくなり、作成を確定できなくなる。生成完了時に一度だけ初期残量を書き換え、以後の増減・能力上限・職業選択・登録は原作に任せる。

生成後の種族基礎能力コピーの最終書込を観測する方式なら、通常・高ボーナスの両経路をまとめて扱える。候補となる書込後PCは次の通り。実装後、binjnesでの実操作検証でもこれらの接続位置が一致することを確認した。

|作品|候補シグナル|その場で変更する先|
|---|---|---|
|Ⅰ|bank 6、書込先$0254、命令$9D90の書込後PC=$9D93、Y=0|$025B|
|Ⅱ|bank 14、書込先$0058、命令$DC12の書込後PC=$DC14、X=5|$0040|
|Ⅲ|bank 14、書込先$0058、命令$DBE2の書込後PC=$DBE4、X=5|$0040|

Ⅰの$025Bは割り振り専用、Ⅱ・Ⅲの$0040は他画面でも使う作業領域なので、アドレスだけで監視・固定せずbankとPCを必ず併用する。設定はQメニューのON/OFFとして追加可能。再抽選・種族変更・作成取消・連続作成・ステート復帰も実装時の検証対象にする。

値はバイナリで、十進64なら0x40、十進60なら0x3C。0x64は十進100なので混同しない。

## 検証と再利用

追加したtools/analyze_creation_bonus.pyは、既存のpy65 1.2.0（BSDライセンス、requirements-analysis.txtの既存依存）で対象ROM内の6502命令を直接実行する。既存ROM識別でコード配置を確認してから固定位置を使う。実装・配布用のCPU/Mapperは引き続きbinjnesであり、このスクリプトは解析用。

- Ⅰ: 実際の原作乱数・生成処理を全65,536初期状態で実行。通常版・変更版の計131,072ケース。NMIや描画を伴わない小区間検証であり、出現確率や全到達値の実プレイ分布は保証しない。上限29の計算と到達例を確認する。
- Ⅱ・Ⅲ: 原作生成処理を実行し、乱数戻り値と描画待ちだけを代用。5種族×初期乱数5通り×追加当選回数8通り＝各ROM200ケース、4本合計800ケース。乱数列そのものの全到達性・確率の検査ではなく、上限処理の分岐検査。
- 6本×5種族＝30組について、64点から原作の加算処理で全能力を上限へ上げ、残りを確認。原作の返却処理ですべて初期能力に戻すと64点へ戻ることも確認。

実行方法:

```powershell
python tools/analyze_creation_bonus.py
```

結果はoutput/creation-bonus-analysis.jsonにROMのSHA-256、作品別最大値、種族別基礎能力・上限・64点からの余り・検証範囲を出力する。手元の通常版と変更版で上記の結果は一致した。

初回解析時にはbinjnes上の実操作・登録までは未検証だった。実装後の検査については次節を参照。


## 実装（2026-10-21）

Q → Difficulty / bonusesのMax creation bonus (species cap)として追加した（assist設定bit 16、初期OFF）。Ⅰ・Ⅱは種族初期能力のコピーから108−基礎能力合計を求め、Ⅲは60点を設定する。上表の最終書込位置で初期残量のみ変更する。割り振り途中でONにしても即補充せず、次の作成から適用する。

既存binjnesのコールバックを利用し、上流コアへの追加変更・新規依存なし。ライセンス・出典は既存third_party/binjnes/と本資料を保持する。

検査はアプリの--creation-checkとtests/check_native_creation.pyを使用する。実際のタイトル→城→町外れ→訓練場→名前入力→種族・属性選択→割り振り→職業選択→登録を操作する。割り振り中のステート復帰で補充されないこと、1点返却と再配分、通常セーブから再起動して登録と能力が維持されることも検査する。PCを作成処理へ飛ばす検査ではない。


検証結果: 通常版・パラメータ変更版の計6本×5種族＝30ケースで、初期配分量、全能力の上限到達、残り0点、返却と再配分、職業選択後の登録、通常セーブから原作を再起動した後の能力・登録維持が成功した。割り振り途中の設定ONとステート復帰で補充が起きないこと、Qメニューの新項目の操作・表示も確認した。

未検証: 全職業・全属性の組合せ、名前変更や作成途中の取消を繰り返す全経路、未知のプログラム改訂。原作の生成完了イベントでのみ介入し、対応を確認できないROMには設定を適用しない。
